# 内嵌工程方法 (Embedded Methods)

仅在 Bug 因果排查、真实设计分支或适用审查时读取；证据模型见 `references/verification.md`，熔断和恢复见 `references/control-plane.md`。

## 1. 因果调试

修改前用最小命令或可观察路径重现问题并保存红灯。若未改代码即为绿，先核对接缝和断言，不能用它证明修复。每次方案都写清症状指纹、因果假说、可证伪预测与直接验证；失败事实进入同一 issue，不能靠换名重置。

因生产条件、偶发时序或缺失数据确实无法复现时，不硬猜“已修复”：记录实际尝试、缺失条件、静态依赖推导和影响，选择可验证的最小改动；最终标 `PARTIAL_UNVERIFIED`，由交付决策处理。假说数量取决于真实分支，不设固定个数。

测试或夹具只有在独立规格证据证明其错误时才修；不得削弱业务断言制造假绿。进入 `REASSESSMENT_REQUIRED` 时先列被证伪事实，再采用实质不同策略。

## 2. 方案与实现

优先沿既有代码和标准能力完成最小垂直切片。只有两个以上真实方案会改变业务结果、兼容性或复杂度时，给出 2–3 个可选方案、推荐项和仓库依据；技术细节已有明确惯例时直接采用。

契约按真实接缝表达：HTTP、事件、函数、CLI、批处理、UI 或纯行为。无接口变更时记录不适用理由，仍冻结行为验收。

保持接口小、实现完整，删除无用抽象和临时代码。刻意采用已知限制的捷径时，按项目注释语法记录 `ponytail: 原因, ceiling: 上限, upgrade: 条件`；没有捷径就不添加债务标签。

## 3. 审查

先按需求轴检查遗漏、范围蔓延和契约偏差，再检查异常、边界、临时资产、深模块和可读性。审查项目按任务风险选择，不套固定清单。涉及输入边界时检查适用的空值、非法长度、并发、幂等、断网或服务错误。

模式要求独立审查时读 `references/subagents.md`。自审只能称对抗自审。任何“通过/完成/修好”都必须引用当前 V ID 和物理证据，不能引用推测或旧输出。
