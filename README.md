## 一、为什么需要 Janus？

随着大语言模型进入存量中大型工程，传统“发一段提示词碰运气”的方式在复杂业务场景中迅速失控：

1. **“假绿”现象（Fake Green）**：模型报告“全部测试通过、功能已完成”，但实际上测试根本没有真实断言、测的是过期的编译产物、或者在测试前临时注释了核心逻辑。
2. **爆炸半径失控（Blast Radius）**：原本只是修改一个字段展示，AI 为了“显得规范”顺手格式化了 50 个无关文件、甚至重构了底层共享基类，导致改动无法审查和回滚。
3. **流程僵化与成本失衡**：要么全无防线（直接改动共享库和关键接口），要么过度设计（改一行代码也执行冗长的全套流程，耗尽 Token 和上下文）。

**Janus 的核心目标**：在严密的授权边界内，以**与风险相称的自适应流程**推进改动，并留下可供工程师随时复核的**真实物理证据**。

## 二、三大工程思想的融合

Janus 并不是规则的简单拼接，而是深度吸收了业界三类核心工程思想，并用控制面将它们组合为自适应闭环：

```text
Matt 契约思想：先把“要做什么、交互结构是什么”说清楚（契约优先、决策剪枝）
             ↓
Ponytail 克制实现：用最小、最深、最少新增依赖的代码实现它（YAGNI、借道重构、债务显式标记）
             ↓
Superpowers 验证闭环：用新鲜、真实的物理运行证据证明结果（红绿循环、对抗式边界检查）
             ↓
Janus 控制面：确保全过程未越界、无漂移，并依据四轴风险自适应选定流程深度
```

## 三、两层控制框架：存储五元与运行三维

在执行任何写操作之前，Janus 首先从物理和逻辑层面划出边界：

### 1. 存储空间五元（文件写到哪里）

| 路径角色 | 含义说明 | 默认控制规则 |
|---|---|---|
| `source_targets` | 本次明确允许修改的源码文件 | 满足对应档位解锁条件后方可写入 |
| `artifact_targets` | 需求、设计、状态记录与验收报告 | 仅允许写入明确列出的产物清单 |
| `scratch_roots` | 构建缓存、运行日志与中间结果 | 位于源码工作区之外，按当次 run 独立隔离 |
| `reference_roots` | 参考工程、附件、样例和第三方库 | 严格只读，禁止执行或修改 |
| `forbidden_roots` | 生产目录、系统路径、敏感凭据 | 严禁写入与执行，敏感路径禁止读取 |

### 2. 运行环境三维（代码运行影响什么）

| 控制维度 | 关注对象 | 典型控制手段 |
|---|---|---|
| `data_scope` | 数据库、Schema、租户与业务数据 | 使用独立测试库；禁止直接对共享生产库做 DDL |
| `runtime_scope` | 系统服务、端口、守护进程与环境变量 | 使用本地受控子进程和临时端口，禁止动用全局服务 |
| `external_effects` | MQ 队列、缓存、短信、支付与出站网络 | 在系统接缝处进行 Mock 隔离，或使用专用沙箱实例 |

## 四、六阶段自适应流水线 (P1 ~ P6)

Janus 将一次完整的研发任务抽象为 6 个严谨的递进阶段：

```text
P1 发现与扫描  ──>  P2 四轴定档  ──>  P3 契约收敛  ──>  P4 垂直实施  ──>  P5 物理验证  ──>  P6 审计交付
 (Facts)          (Triage)         (Design)        (Implement)      (Verify)       (Delivery)
```

- **P1 发现（Discovery）**：全面扫描目标工程依赖、构建/测试入口、已有 Git 修改与路径角色，建立初始事实基线。
- **P2 定档（Triage）**：根据四轴风险评分（I 接口 / D 数据 / C 契约 / R 回滚），生成结构化**定档卡（Risk Scorecard）**，确定进入 R0、R1 还是 R2 车道（只升不降）。
- **P3 设计（Design）**：跨端改动前冻结字段级契约（类型、必填、默认值、状态码），排除业务歧义，应用深模块与决策前沿剪枝。
- **P4 实施（Implement）**：沿真实数据流做**垂直切片**（数据层 → 逻辑层 → API → UI），在锁定的白名单写集内实施最小修改。
- **P5 验证（Verify）**：从低成本到高成本逐步运行构建、定向单测、接口调用与端到端探针，产出完整物理证据链。
- **P6 交付（Delivery）**：比对工作区排除未归因漂移，汇总验证结论、遗留项与 `// ponytail:` 债务标记，生成聚合审计报告。

## 五、三车道与五道确认门

### 1. 三种自适应风险车道

| 车道 | 适用场景 | 流程深度 | 门禁要求 |
|---|---|---|---|
| **Spike** (快速探针) | 原型验证、纯技术预研 | 只读探测与概念验证 | 禁止修改生产代码 |
| **R0** (轻量快车道) | 单文件、单点局部修复、低影响微调 | 最小写集 + 最小物理验证闭环 | 验证通过后直接交付，无需复杂审批 |
| **R1** (标准主车道) | 单模块 CRUD、前后端常规联动改动 | 契约冻结 + 垂直切片 + 双向比对验证 | 核心项验证有效后直接交付 |
| **R2** (严格风控道) | 跨业务域、新增表结构、复杂迁移、核心鉴权 | 完整架构方案 + 实施写集审批 + 候选包冻结 | 强制依次通过 **Gate 1 ～ 5** |

### 2. R2 严格档的五道确认门

```text
P1 发现 → P2 定档 ──> Gate 1: 需求与业务边界确认
                          ↓
P3 设计与契约 ────> Gate 2: 增量架构确认 ──> Gate 3: 详细设计与字段契约确认
                          ↓
P4 实施前 ────────> Gate 4: 源码写集白名单 (Action Manifest) 审批
                          ↓
P4 实施 → P5 验证 ──> Gate 5: 物理验收证据裁决 ──> P6 审计交付
```

## 六、可靠性机制：终结假绿与盲改

### 1. A/V 三表多对多追踪矩阵
Janus 把“业务诉求”与“执行证据”彻底解耦：
- **Acceptance Ledger (A 表)**：列出每条具体业务断言（A1, A2...）；
- **Evidence Ledger (V 表)**：记录每次执行的精确命令、运行环境、控制台真实输出及**当次源码 Git SHA 哈希**；
- **Trace Matrix (T 表)**：构建 A 与 V 的多对多映射，判定每项断言的最终结果（PASS / FAIL）和证据有效性（VALID / INVALID）。

### 2. 真实物理证据法则
- 绝不把 `exit 0`、HTTP 200 或控制台没有红字当做“通过”。
- 所有的“通过”必须绑定当次运行环境、被测构建产物哈希与真实的业务断言。
- 修复 Bug 时，优先观察未修改代码在验证下的**真实失败**，再证明修改后的**同一方式成功**（红绿对抗）。

### 3. 熔断与未归因漂移拦截
- **3/5 故障熔断**：单点修复连续尝试 3 次失败或总计失败 5 次，立即熔断停机，保全现场，请求人类决策。
- **漂移拦截**：交付前比对工作区，任何未在事先申报写集内的文件改动（即使是空行或注释格式化）均判定为非法漂移，直接阻断交付。

## 七、快速开始与安装

### 方式一：发送给 Agent 自动安装（推荐）

直接将本仓库或 `janus/` 目录发送给支持 Skill 的编程助手（Codex、Claude Code、Trae 等），并附带指令：

```text
帮我安装这里面的 skill：janus，将其配置为全局 skill，并适配当前 agent。
```

### 方式二：手动配置为 Codex 全局技能

将 `janus` 目录完整复制到本地 Codex 技能根目录：

```powershell
# Windows
Copy-Item -Path .\janus -Destination "$env:USERPROFILE\.codex\skills\janus" -Recurse -Force

# macOS / Linux
cp -r ./janus ~/.codex/skills/janus
```

## 八、实战使用指南

### 1. 显式调用格式

在对话中使用 `$janus` 显式触发：

```text
$janus [具体业务需求或缺陷修复描述]
目标工程：[代码所在的绝对路径，例如 X:\MES\web_08 或 /workspace/my-app]
参考工程：[若有只读参考代码可填写，无则留空]
核心要求：[例如：前后端字段必须向后兼容 / 必须有真实接口调用证据 / 严禁改动数据库]
```

### 2. 进阶：多模型子代理对抗审查

对于复杂工程或 R2 级风险改动，单一 Agent 极易产生思维盲区。Janus 在设计上天然支持引入独立模型做对抗审查：

```text
完成方案与代码修改后，交给独立子 Agent 开启高思考档位进行对抗审查，重点排查边界异常、死锁风险与并发安全。
```

## 十、质量验证与维护

`janus` 技能包内附带严格的自测与哈希校验套件，可在 PowerShell 5.1 或 PowerShell 7 中运行：

```powershell
cd janus

# 1. 源码模式静态合规检查
powershell -ExecutionPolicy Bypass -File .\scripts\validate-fullstack-skills.ps1 -Mode Source

# 2. 全量故障注入断言与安全回归自测
powershell -ExecutionPolicy Bypass -File .\scripts\validate-fullstack-skills.ps1 -SelfTest

# 3. 发行模式完整闭包哈希校验
powershell -ExecutionPolicy Bypass -File .\scripts\validate-fullstack-skills.ps1 -Mode Release
```
